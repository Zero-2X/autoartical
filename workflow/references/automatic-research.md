# 选题自动研究工作流

本仓库将本机 autoresearch 中有用的研究部分收敛为一个轻量入口，不复制其后台循环、tmux 执行器或演示文稿系统。入口位于选题说明之后、正文规划之前，保留研究契约、证据映射、实验协议和 Gate。

## 顺序

1. **领域定位**：确定领域名称，说明研究价值，并绑定权威背景证据。
2. **子领域收敛**：把泛主题收窄为任务、对象和边界，说明为什么选择这个方向。
3. **挑战与影响**：拆成可观察失败模式，写清影响和可测后果。
4. **Current methods**：按机制而不是项目名称分类；每类记录代表工作、优点、缺点、适用边界和来源。
5. **关键缺口**：用“方法缺陷 → 未解决矛盾 → 研究问题”闭环。
6. **科学设计**：每个组件对应一个缺陷、机制假设、可证伪预测和验证方式。
7. **案例与实验**：case study 解释机制和失败边界；主实验用 benchmark、强 baseline、明确 metrics 和成功判据验证主张。

## 门禁

`run_research.py` 读取 `idea-card.json` 和证据台账，生成 `workspace/research/research-brief.json`、`research-plan.md` 与 `research-gate.json`。它可以自动生成研究问题和证据缺口，但不会把查询计划写成事实。缺少领域／子领域来源、方法分类证据或实验协议时，Gate 为 `needs_research`；补充 `external_evidence` 后重跑。

首次运行生成可供研究代理填写的 brief 骨架；后续运行默认保留已有 brief，只重算 Gate，避免补充资料后覆盖研究结论。需要重新开始时显式使用 `--reset`。

主实验至少表达四个问题：主效果、组件贡献、鲁棒性／效率／边界、案例机制解释。benchmark、baseline 和 metrics 不是购物清单：每项都要写清它回答什么、测量什么、支持哪条 claim。结果出来后再进入结果分析和正文，不能预先写成优势结论。

## 与现有流程的关系

自动研究复用现有 evidence ledger、来源指纹、冲突检测和引用核验；选题候选仍保留人工选择；章节写作仍由现有逐章审计负责。旧研究参考材料保留为背景文档，新的可执行入口只有 `run_research.py`，避免两套状态系统并行。
