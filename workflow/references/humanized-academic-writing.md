# 专业化与作者化写作契约

## 目标

把“降低 AI 味”落实为可审计的写作质量：保留事实、数据、引用、术语、条件和结论强度；删去无信息的铺垫、空泛拔高和重复收束；让句式节奏与论证重点随内容变化。工作流不承诺通过任何商业 AI 检测器，也不通过插入错别字、伪造经历或改写成口语来伪装作者身份。

## 固定流程

1. **扫描**：按段定位空泛价值判断、模糊归因、过度对称的并列、重复段首、堆叠限定词、无主语被动句、标题复读和段末套话。
2. **保护**：锁定数字、单位、引用、公式、变量、数据集、图表编号、否定/条件/归因和结果等级；这些字段不得被润色器擅自改动。
3. **局部修改**：优先删除填充短语或改动句内结构；只有段落逻辑确实不清时才重排段落。每次修改写入 diff 或审查记录。
4. **人工化复核**：检查作者判断、限制条件和意外发现是否真实存在；没有来源的“研究表明/专家认为”必须落到具体文献或改成有边界的本文判断。
5. **回归**：重新检查引用、数字、图表、章节长度、段落重复和证据等级；若改写让语体变口语、结论变强或删除了限制，回滚。

## 适用于中文科技/计算机文本的硬约束

- 泛化收尾（“具有重要意义”“前景广阔”“提供新思路”）不作为独立结论；改为具体贡献、可检验推论或局限。
- “专家认为”“研究表明”等无出处归因不得进入定稿。
- 同一段中三个以上等长并列只有在确有三项对象时保留；不要为了打散而删掉真实功能或实验条件。
- “基于……理论/框架”不是禁词，但连续段首出现时移到解释位置，并先陈述现象或问题。
- 结论强度必须与证据等级一致：案例只能支持案例观察，单一数据集不能写成普遍泛化，计划不能写成已完成。
- 学术语域保留必要术语（如“进行训练”“显著性检验”“基于数据集”）；只删除翻译腔、无对象的复杂系动词和重复限定。
- 允许句子长短变化，但不通过错别字、随机标点或无依据的第一人称经历制造“人味”。

## 证据强度分档（跨节一致）

同一主张在摘要、正文、讨论与结论中使用同一档措辞；档位只能随证据增强而上调，不能在结论或摘要里“升级”。

| 档位 | 适用证据 | 中文措辞 | 英文措辞 |
|---|---|---|---|
| 因果档 | 本文的受控实验、消融已实测 | 证明、表明、使……降低 | show, demonstrate, identify |
| 关联档 | 相关性结果、文献间的一致证据 | 提示、支持、与……一致 | suggest, indicate, is consistent with |
| 推测档 | 机制推断、未实测的设计预期 | 可能、预期、本文推断、若……则 | may, could, we speculate |
| 缺口陈述 | 文献未覆盖 | 尚缺少、仍未系统评测、尚不清楚 | remains unclear, is largely unexplored |

计划书（结果“待实测”）中，凡主语是本文方法的句子只能用推测档或写成可证伪假设；`cross_section_audit` 会拦下“本文方法显著提升/证明了……”而无计划标记的句子。

## 跨节一致性审计

`manuscript_lint.py` 调用 `cross_section_audit.py`，对全文做以下检查（失败项阻断交付，提示项需人工决定）：

1. **结论强度**：本文工作的因果档措辞在实验待实测时失败。
2. **背景断言须有引用**：“研究表明”“普遍认为”“被广泛应用”等所在句没有 `[n]` 即失败。
3. **术语表**：`document_plan/glossary.json` 中 `terms.<首选>.avoid` 的变体出现即失败；`names` 列出数据集与方法名。
4. **缩写首次出现须展开**：AP、IoU 一类通用缩写首次出现时给出全称或中文释义；紧跟引用的专名（数据集、方法）不在此列。
5. **章首承接**：第2章起，每章首段应点明它回答前文留下的哪个问题。
6. **数字格式**：千分位与不分隔、百分号前空格的写法不混用。
7. **引用密度**：报告各章每千字引用数；综述章节偏低时提示。
8. **套话分级**：宣传性套话（“赋能”“具有重要意义”“前景广阔”“综上所述”，英文 delve into、shed light on 等）失败；轻度套话（“值得注意的是”，英文 moreover、robust 等）提示。英文摘要中的 em dash 失败。

## 修订的防捏造回溯

任何润色、改写、翻译、压缩之后运行

```bash
python workflow/scripts/revision_guard.py <修改前.md> <修改后.md> --allow-file <topic>/workspace/quality/revision-allow.txt --out <topic>/workspace/quality/revision-guard-<日期>.json
```

修改后出现、但修改前不存在的数字（含单位）、引用编号、图表式编号、英文专名与缩写都列为 `untraceable_tokens`；列表非空即失败。确属公共知识的展开（如 GPL 的全称）写入允许清单并注明理由，研究事实不得进允许清单。被删掉的数字与引用列在 `dropped_tokens`，需要在修订记录中说明。判定原则：把原文拿走后，这个词是否就失去依据。

## 修订记录（每次实质修改都写）

| 字段 | 内容 |
|---|---|
| `scope` | 修改的章节与段落 |
| `logic_line` | 本段/本节的论证线，例如“基准类别有限 → 业务查询开放 → 需要开放词汇方法 → 可靠性是使用前提” |
| `rules_applied` | 采用的规则（证据分档、一段一论点、术语表……） |
| `ai_tells_removed` | 删去的套话 |
| `untraceable_tokens` | 来自 `revision_guard`，必须为空 |
| `dropped_tokens` | 删去的数字或引用及理由 |

需要压缩篇幅时，可同时给出约 60%–70% 长度的紧凑版供作者比较；紧凑版只删去括注与重复限定，保留主张、机制、引用和全部修正。

## 复用的开源方法

- `op7418/Humanizer-zh`（MIT）：保留事实、确定程度和作者声音，按语体和密度判断模式；仓库页面显示 2026-09-23 更新、约 18.7k stars。吸收其语体识别、保真改写和“不要机械删除正常排比”的原则。
- `blader/humanizer`（MIT）：用模式清单识别“ staged run-up、强凑三段式、空洞收尾、堆叠限定”等结构问题，强调为读者改善文字而不是追求检测器分数；仓库公开页面显示 97 commits 和持续维护。
- `zkrun/academic-humanizer-zh`（MIT）：把表层扫描、语义复核、事实保护和前后对照分开；当前仓库规模较小，因此只吸收其可解释报告和“检测—局部修订—重测”闭环，不把示例分数当成外部检测器结果。

- `mumdark/nature-writing-studio`（2026-08-29 更新，约 128 stars，**未声明许可证**）：从 Nature 论文统计英文句式库，并设回溯式防捏造验收层、证据强度动词分档、跨节一致性规则和三级 AI 套话表。由于未授权，本仓库没有复制其 TSV 知识库或提示词；只把“回溯检查、分档措辞、跨节审计、逻辑线与修订记录”的方法用自写代码实现，见 `revision_guard.py` 与 `cross_section_audit.py`。英文论文需要 Nature 风格句式时，可由用户自行安装该 skill 作为可选的英文润色步骤，但其输出必须再通过 `revision_guard.py` 与本仓库的引用、证据门禁。

本仓库不直接复制这些仓库的代码、提示词或资源；只把公开方法转化为本地 style gate 和技能规则，并保留来源链接与许可证记录。
